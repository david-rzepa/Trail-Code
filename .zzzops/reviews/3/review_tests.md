# G3 setup test review

Changes requested. The proposed tests describe useful basic Go and Node fixtures, but they do not yet cover key approved setup and maintenance behaviors. The proposed `src/test-impact/setup-cli.ts` is one possible invocation seam; the approved design requires an explicitly invoked skill and packaged generation assets, not this exact standalone CLI. Tests should exercise the chosen supported production entry point without forcing an otherwise unnecessary public interface.

1. The positive Go/Node fixtures assert an `execution_units` list and a success status, but do not demonstrate that selected tests actually ran or excluded tests did not. Both tests are passing before and after the changed source; a fabricated execution report would pass. Instrument test execution with controlled markers, include a failing affected test and a passing unchanged unrelated unit (or otherwise prove subprocess execution and exclusion), compare with the full runner, and exercise the actual Trail-code representative setup and nonrecursive `npm test` fallback. Required Go consumer dependency must execute, not just appear in output.
2. The approved design requires a usable installed distribution and safe maintenance. Add focused tests that package a fresh distribution and invoke its actual supported setup asset without the source checkout, then verify unchanged reruns, changes in workflow/additional project, user edits and an ambiguous/conflicting full command preserve user content and fail or broaden rather than silently overwrite. Include missing/incompatible helper and no manufactured passing receipt on failure. A single adapter-byte idempotence assertion in the current checkout does not cover these requirements.
3. Selection safety and discovery failures have no setup-level tests. Add representative executable coverage for an unknown/new runner or project, incomplete/failed discovery and malformed or incomplete requirements, as well as cross-project/mixed-language dependencies or an unmodeled resource; confirm the generated integration cannot claim valid sparse/empty success and uses a justified full fallback or reports a gap. Verify normal endpoint rejection/target mismatch and failure propagation from generated adapter in addition to the worktree string case.
4. The trust assertion is masked by the symlink rejection: setup can stop before reading the injected instructions, so this does not test whether malicious data affects a successful setup. Separate the cases. With ordinary destinations, inject commands and suite-dropping instructions in representative lower-trust content, require no side effects or omitted mandatory workflow, and include legitimate applicable project instructions. Keep an independent unsafe-destination regression. Cover representative paths and not claims of automatic compatibility with unsupported host installers.

The recorded 323 ms red run exits before setup exists and therefore cannot establish actual behavior or integration cost. Remeasure after implementation and keep repeated full journeys only where needed to prove real execution or maintenance; fixture-level focused tests can cover the other cases. No tests should demand evidence of uninterrupted checkout stability.
