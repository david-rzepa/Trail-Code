# Conservative two-snapshot impact analysis

## Outcome and scope

Extend this public Trail-code fork directly with deterministic, conservative impact analysis, preparing the change for a future upstream pull request. The analysis supplies a versioned report describing affected code and unresolved coverage, not a test execution or passing result. The consumer must broaden or refuse verification when the report cannot safely support exclusion. The requirements and acceptance matrix in `docs/test-impact/design.md` apply as amended by the owner’s committed-endpoints-only and ordinary stable-input runner directions; this design focuses on the analyzer foundation and does not duplicate the adapter or setup skill.

## Approach

Work directly in `https://github.com/david-rzepa/Trail-Code`, integrating on `test-impact` from upstream base `ca20a67764e99531a1cf272eea8354e2c16f71d9` (Trail-code 0.28.0, MIT). Preserve the separate Unity plugin branch and upstream attribution and license. Build changes as an upstreamable extension in this repository; no separate repository or Git subtree is involved. Use existing parser, per-file facts, resolution and graph traversal. The current `src/graph/resolve.ts` deliberately drops unresolved calls, `src/blast/diff.ts` implements navigation-oriented ranges, and `src/blast/blast.ts` uses presentation groups. Add a separately identified conservative path instead of changing their meaning or consuming their `testModules` as a test inventory.

Resolve both requested refs once to immutable commit and tree identities using argument arrays. Compare the exact trees, never their merge base. Read committed Git tree objects directly or materialize their bytes in independent temporary directories without changing the user's checkout. Analysis must not rely on Btrfs, snapshots, special mounts, elevated privileges or any particular filesystem; operate on ordinary Git repositories across supported platforms. Pin and report commit and tree IDs, preserve modes and paths needed for accurate analysis, and treat unavailable Git objects, unsupported path representation, missing required submodules or failed materialization as explicit failure or unbounded gap, never as unchanged input. Worktree capture is deferred and the literal `worktree` is rejected clearly. Treat committed symlink entries as link metadata and bytes, never blindly follow them through the host filesystem. Resolve a link dependency only when every link in the chain and the target are proven to be entries of the same pinned Git tree with supported semantics; absolute targets, parent escapes, loops, missing targets, platform ambiguities or unsupported link handling produce an explicit unbounded gap and full-profile fallback (or stop if safe analysis cannot proceed). No external target bytes may enter analysis under the claimed snapshot identity. Materialization must validate path components and perform no-follow, root-contained creation, reads, writes and cleanup; reject traversal, pre-existing links or any platform condition that prevents proving containment rather than attempting an unsafe operation. Work on private temporary roots, but do not assume their location alone makes dereferencing safe. The execution layer uses the ordinary test runner with a practical preflight against target B and reports the observed target and stable-input assumption. It does not claim proof that inputs remain unchanged throughout the run or require continuous monitoring, special filesystems, isolated checkouts or mutation detection. The analyzer report identifies analyzed commits, not the state of later execution.

Build file facts per snapshot using existing extraction caches only when extraction contracts match. Extend extractor and resolver outputs to record evidence and limitations rather than dropping unresolved candidates, parse failures or unsupported relevant input. Retain every defensible candidate and full provenance; represent unresolved bounded scopes explicitly. Unknown or unbounded behavior, unknown scope boundaries, incomplete input enumeration and analysis failures produce an unbounded gap requiring full-profile fallback. A successful parser invocation or absence of an edge does not imply completeness. Treat reflection, dynamic dispatch, callbacks, registration, subprocesses and resources as potential gaps unless modeled or safely bounded; document language-specific supported constructs and demonstrate why a scope is safe before labeling it bounded. External/environment inputs remain execution-layer configuration and must not be inferred unchanged from Git.

Perform a whole-graph resolution per snapshot after reusing compatible raw facts. Compute reverse closure without hop or count caps on old and new graphs separately, retaining revision provenance and scope-level dependencies. Seed old and new entities for changed files; use old edges for deleted entities/files and new edges for additions and new bindings. A conservative file/scope seed can broaden beyond changed lines where symbol attribution is uncertain. Where rename identity is ambiguous, treat as delete plus add. Re-resolve unchanged callers after symbol table changes. Emit all affected files/entities plus justified scope fallback, not only nodes that resemble tests. Any cross-scope boundary not demonstrably complete widens to the whole profile.

Use a separate conservative cache namespace and atomic writes. Keys include snapshot identity, path and content/metadata as relevant, analyzer and grammar/extractor/resolver versions, configuration, and conservative policy/mode. Graph caches may only satisfy the exact identity and successful complete refresh; stale data, failed writes or unsupported cache versions never masquerade as current. Prefer rebuilding to unsafe cache reuse. Stable path ordering and reason ordering make identical inputs produce identical reports.

## Report contract

Retain and validate the conservative schema version 1 as described in `docs/test-impact/design.md` section 8. Include `schema_version`, `analysis_identity`, `comparison` (requested and resolved endpoints, tree/snapshot identities), `changes` (old/new paths and entities), `affected` (complete files/entities and revision/reason provenance), `analysis_gaps`, `required_fallback_scopes`, and `analysis_status`. Define enumerated gap/status variants and a schema/validator in the implementation; reject unsupported versions and missing mandatory identity or status. Stable, structured reasons must distinguish direct changes, graph dependencies and fallbacks. A bounded gap identifies both the scope and the rationale for its boundary; an unbounded gap demands full-profile fallback. Deterministic sorting and canonical identity calculation are part of the contract. No graph-derived text is executable shell input. The impact report is distinct from the downstream plan, runner inventory, execution result and receipts.

### Observable analyzer interface

`trail impact --from <commit> --to <commit> --json` requires both options exactly once; help/version are exempt. Commit values are resolved once with Git to immutable commits and trees; `worktree` is rejected explicitly as unsupported. An unknown ref, invalid or missing option, or unavailable commit snapshot returns nonzero (2 for invalid input or incomplete invocation), does not emit an apparently valid report, and writes diagnostics to stderr. `--json` writes exactly one JSON object to stdout for a completed analysis, with diagnostics on stderr. Exit 0 means the report was produced, including when `analysis_status` requires fallback; it never means tests passed or verification succeeded. No model calls are made. Existing `trail blast` semantics stay unchanged.

The following minimum v1 shape makes acceptance tests and adapters observable; all arrays are present even when empty, and all paths are repository-relative POSIX strings. Object fields listed below are mandatory unless explicitly nullable. Unknown schema versions are rejected; the downstream validator must treat malformed or unknown status, missing required fields or a contradictory status/fallback as unusable and broaden or block. Additions that consumers do not understand never justify a narrower selection.

- `schema_version`: integer `1`.
- `analysis_identity`: object with nonempty strings `analyzer_version`, `grammar_identity`, `extractor_identity`, `resolver_identity`, and `policy_identity`, plus `mode` equal to `conservative`.
- `comparison`: object with `from` and `to`. Each has `requested` (the literal argument), `kind` equal to `commit`, `fingerprint` (nonempty content identity), `commit` and `tree` (full Git object IDs). The fingerprint identifies analysis inputs, not future execution.
- `changes`: array of objects with `kind` (`added`, `modified`, `removed`, `renamed`), `old_path` and `new_path` (strings or null). Added requires only new; removed requires only old; modified requires both equal paths; renamed requires both distinct paths. Include old and new entity references where available as `old_entities` and `new_entities`, arrays of identifiers. An uncertain rename is represented as removal and addition.
- `affected`: array of objects with `revision` (`from` or `to`), `path`, `entity` (string or null for file/scope impact), and nonempty `reasons` array. Each reason has `kind` (`changed`, `dependency`, or `fallback`) and `detail` (nonempty string); dependency reasons carry their supporting relationship/provenance. Output retains all relevant old and new impacts without result truncation; it does not filter by test filename.
- `analysis_gaps`: array of objects with `revision` (`from` or `to`), `path` (string or null for global gaps), `kind`, `detail`, and `scope` (null for unbounded, or a nonempty declared scope identifier). Reasons include parse/index failures, unresolved constructs, unsupported or unmodeled behavior, and missing required input.
- `required_fallback_scopes`: array of objects with `kind` (`scope` or `full_profile`), `scope` (nonempty identifier for `scope`, otherwise null), and `reason` (nonempty). Every unbounded gap requires `full_profile`; bounded gaps require an appropriate dependent scope or full profile. Scope identifiers are data, not shell fragments, and the adapter must be able to map them to dependent targets or fall back to the full profile.
- `analysis_status`: `complete` only when the supported model has no uncovered gaps, `bounded` when every gap is covered by explicit bounded fallback, and `incomplete` when any gap is unbounded. An incomplete report always has a `full_profile` fallback. A valid empty impact has an empty `affected` array and no gaps; it is distinct from a failed capture or incomplete report.

Order changes, affected entities, gaps, fallback scopes and reasons by stable documented keys; all identity and policy inputs are included in cache keys. Test the CLI as a subprocess against temporary repositories, validate every required field and type, and check that malformed/unsupported schema data cannot be used to justify exclusions. Include explicit error, incomplete-with-fallback and valid-empty examples. A commit/tree identity identifies the analyzed source, not a proof that runner inputs remained unchanged.

## Conditional schema v2 and supported model

Preserve the existing default `trail impact --from A --to B --json` as schema v1, with its existing conservative fallback and no conditional claims. Request v2 explicitly with `--schema-version 2`; `--schema-version 1` is equivalent to the default. Reject unsupported values. Version 2 retains v1's required identity, comparison, changes, affected, gap and fallback fields, and adds `supported_model` and `context_requirements`. V1 consumers must reject schema version 2 rather than treating it as v1, and neither v1 fallback nor report output may be weakened by the presence of v2. Continue to reject `worktree` in both versions.

A v2 report can set `analysis_status` to `conditional` only if the selected model covers discovered tracked source dependencies subject to every stated context requirement and any uncovered dependencies have independently justified bounded fallback scopes. `conditional` is distinct from `complete`, `bounded` and `incomplete`: it never means the context has been validated or tests passed. V2's `supported_model` contains nonempty `id` and `version` strings; identity changes whenever its dependency semantics or requirements change and is included in cache and receipt compatibility. Each mandatory `context_requirements` entry has a stable `id`, `kind`, typed `predicate` descriptor and `evidence_kind`; all entries are mandatory, unique and deterministically ordered. A predicate specifies what must be established, not a fabricated value for facts unknown to the standalone analyzer. Document the allowed kinds and values in the v2 schema and reject unknown kinds or versions. A conditional report has a nonempty requirements list and cannot also claim unconditional completeness. Gaps that cannot be proven bounded remain incomplete with `full_profile`, even under a conditional model.

### Independent model contract and evidence bindings

G2 maintains a versioned, locally trusted registry keyed by the exact `supported_model.id` and `version`, independently of the analyzer's report. Each registry entry defines the complete mandatory requirement IDs, exact kinds and admissible evidence bindings, predicate shapes and allowed parameters, trigger predicates and validation rules. The report cannot define or weaken this registry. At minimum every conditional report requires these singleton IDs: `runtime` (runtime version, platform and architecture observed from the actual process), `runner` (runner/adapter executable identity, version, discovery policy and profile), `inventory` (actual discovered targets and scope bound to target commit and profile), `resolver` (actual compiler/transpiler, module resolution and loader configuration), `inputs` (committed source and declared generated/external input inventory), `environment` (declared relevant non-secret identity or secure fingerprint), and `baseline` (compatible receipt identity, coverage and context). Every ID has a registry-defined evidence kind and collector; a self-reported expected value, a mere claim of absence or a weaker collector cannot stand in for required independent observation. Record collector/version, subject identity and observed digest; bind evidence to target commit and tree, profile, inventory, model version and actual execution configuration, and validate for the planned execution and receipt under the reported stable-input assumption; this does not require continuous observation.

The standalone analyzer receives only the committed endpoints and report-version selection. It can supply fixed predicates and parameters derived from the pinned trees and the model, such as commit/tree IDs, tracked-path set, supported module syntax and resolver constraints; it must not invent a runner, profile, test inventory, local receipt or execution environment value. For execution-only facts it emits registry-defined descriptors, for example `{ "id": "inventory", "kind": "inventory", "predicate": { "op": "complete_inventory_for_target_and_profile" }, "evidence_kind": "runner_discovery" }` and `{ "id": "baseline", "kind": "baseline", "predicate": { "op": "compatible_passing_receipt_for_from_and_profile" }, "evidence_kind": "receipt_validation" }`. The registry pins each ID to its permitted operation, parameter shape and collector; the actual profile, discovered target set and receipt ID are independently bound by G2 at planning time, not guessed or trusted from the report. The runtime, runner, resolver, inputs and environment descriptors likewise state registry-defined supportedness, consistency and completeness predicates; G2 obtains the actual values from its collectors and evaluates those predicates. A descriptor that asserts an execution value, changes an operation or weakens parameters is rejected unless the independent registry explicitly permits it. Analyzer-derived parameters are independently checked against the pinned commits and registry constraints before use.

The registry also defines deterministic triggers from independently discovered actual configuration and inventory: each loader/hook/plugin, resource/fixture/service, generated input, external dependency or relevant environment input produces a uniquely keyed mandatory requirement with its own registry-prescribed collector, identity and fingerprint. The registry specifies how absence is established by complete discovery of each class, rather than inferring absence from an empty report. If discovery, a trigger, a dependency boundary, a collector, or an evidence binding is unavailable or incomplete, conditional sparse use is forbidden and the full profile is required (or verification stops when full execution cannot safely validate B). Adapters must derive the required singleton and triggered sets independently, then compare the report's exact IDs, kinds, types, trigger subjects and evidence bindings with that derived set before evaluating values. Reject missing, duplicate, substituted, extra unknown, inconsistent or weaker entries and require fallback; the analyzer cannot suppress a requirement by omitting its entry. Registry changes that affect semantics or evidence bump model version and invalidate incompatible caches, plans and receipts. This permits sparse execution for a small conventional project whose runtime, runner, inventory, static resolver and inputs are fully discoverable and independently verifiable; it does not require a hypothetical unknown dependency to be asserted absent without evidence.

### Multilingual dependency coverage and scope boundaries

The general analyzer reuses Trail-code's existing multilingual parsing, extraction, build and resolution layers; admission is based on declared construct coverage and defensible dependency boundaries, not a whole-repository Node/TypeScript whitelist. Record a versioned coverage matrix per language and construct, including supported path/import/build resolution and explicit unsupported or uncertain behavior. Parsing success and the presence of navigation edges are not evidence of dependency completeness. The conservative fact pipeline must preserve raw imports/re-exports and module-level effects, file and build-target facts, unresolved references, and all justified ambiguous candidates with source/revision provenance. In particular, ordinary upstream resolution drops unresolved calls and may narrow ambiguous targets; preserve candidates before such narrowing and do not treat its omission as evidence of no dependency. A facts cache that omits imports cannot establish complete file dependencies: extend and version its extraction contract, invalidating incompatible cached facts. Re-resolve both full snapshot graphs after extraction and traverse complete reverse closure across symbol, file, import and declared build-target relationships, retaining change reasons.

Model each ecosystem with a versioned language/build adapter or combination of adapters and context requirements. Examples include Node/TypeScript imports and exports, Python module/package imports and import-time effects, and Go package imports/build targets. Each adapter must declare precisely which resolution forms, dynamic constructs, input kinds and configurations it covers and produce explicit gaps for others; supported ecosystems and constructs are established by implemented evidence, not their parser's language name. Composite/mixed-language models must report every component model identity and requirement set and account for cross-language, subprocess, generated, resource and build relationships or broaden accordingly. An ordinary irrelevant documentation or metadata file is not by itself a global fallback: classify each changed or relevant input via explicit applicable rules, and if its effect is unknown apply a justified dependent scope or full fallback. Never infer irrelevance merely from filename, ignored status or directory.

Bounded gaps carry a machine-readable scope ID, dependency boundary, provenance and reason, with the model/version and evidence sufficient for G2's independent registry to validate the boundary. The scope represents a build target, package or other declared unit with a demonstrated complete relationship to its dependents; select all dependent tests, including outside that scope, via both revision graphs and declared target mappings. A directory alone is not a boundary. If boundary completeness, cross-scope edges or mapping cannot be established, use `full_profile`; do not global-fallback when a bounded dependent scope is actually proven. Context requirements and their independent evidence apply to every selected component model. A conditional report may carry bounded gaps and required scopes, but cannot claim unconditional completeness and must fall back fully for an unbounded gap or unmet requirement.

### Minimum useful supported slices

The initial acceptance gate requires working, selective models for both a conventional Node/TypeScript static-module project and a Go module with statically resolved package imports and package-level `go test` targets. For the Go slice, derive package relationships from tracked source and `go.mod`/build configuration and include package initialization and `_test.go` dependencies in both revision graphs. The supported model must explicitly state Go version, build tags and platform conditions and verify that the configured target inventory and import resolution match the execution context. Treat unresolved imports, cgo, build constraints or generated/embed inputs not demonstrably covered as bounded gaps only with a proven complete dependent boundary; otherwise require full fallback. External modules and tools are subject to the same verified-context rules. This minimum does not imply every Go construct or all projects are supported; additional Python and other language fixtures test declared supported constructs and appropriate fallback.

For committed endpoints, analysis reads pinned Git trees without requiring the caller to check out either commit or prove their checkout is clean. A changed or dirty current checkout cannot influence analyzer results. The separate execution layer performs its practical target preflight and reports its stable-input assumption.


Requirements cover at least: runtime and platform/architecture identity and supported module semantics; runner, selection/discovery adapter and version with actual inventory and configured scope; module loader, resolver, aliases, compiler/transpiler, hooks and plugin identities/configuration; source and generated input inventory; external dependencies, resources, fixtures and services and environment values that can affect discovery, execution or module resolution; and baseline receipt/profile compatibility. Use fingerprints or non-secret descriptors rather than sensitive raw environment values. A requirement is satisfied only by independently obtained evidence bound to the actual target snapshot, profile, inventory and execution context; a user-declared assertion or mere matching string from the report cannot substitute for observing the corresponding input. When reliable independent evidence cannot be obtained, G2 must execute the full configured profile or block if even that cannot validate the requested target. Scope mapping that cannot include dependents likewise falls back to full profile. Full fallback preserves the original workflow, performs the same practical target preflight, and reports the stable-input assumption.

G2 must parse and validate v2 completely before using its impact: validate schema and exact model/version allowlist, identities and every required kind/value against evidence from the actual execution context. Unknown, missing, malformed, unsupported, stale, mismatched or unmet requirements, model identities or evidence forbid sparse use and trigger full-profile fallback or explicit failure when a valid full run is impossible. The plan reports each requirement and validation result and distinguishes calculated impact from executed scope; a successful conditional sparse run may produce a receipt only after all checks, compatible baseline, practical target preflight and complete execution pass, with the stable-input assumption recorded. Prior receipts must match the model, requirement set and execution context and cannot convert a conditional report into unconditional completeness. This is a dependency contract for G2, not a claim that G1 executes tests.

Acceptance uses representative real Node/TypeScript, Python and Go project fixtures with their normal manifests, source and test layout, plus two independent runnable test targets in each supported slice, a compatible baseline and verified context. At minimum both the Node/TypeScript and Go fixtures must produce a real conditional sparse result and a G2 sparse execution; a Go full-profile result cannot satisfy the non-Node gate: a change isolated to the first dependency chain selects its dependent target while excluding the unrelated target, and the full suite serves as comparison. For Go, use separate packages A and B with independent tests and tracked imports, change a source in A, and assert that `go test` runs A and every dependent test package while B is excluded; compare with a full module run and include the inverse/deletion/import-change cases. Verify ordinary configuration and non-code inputs follow explicit rules without automatically forcing global fallback, and test a bounded uncertainty whose dependent tests cross its scope, an unbounded gap requiring full fallback, changed/deleted imports and rebinding in both revisions, and mixed-language/build dependencies. Test A and B without checking either out, including with an unrelated dirty checkout. Separately introduce dynamic module loading, plugin/discovery changes, resource and fixture dependencies, import-time side effects and unknown loader or environment inputs: every affected dependent target must be included, or selection must broaden to the full profile; an unknown or falsified requirement must never produce sparse execution. Exercise v1 default and explicit v1, explicit v2, unsupported versions, malformed/unknown requirements, changed context/model identities and a v1-only consumer rejecting v2. Remove each singleton requirement in turn, substitute a weaker evidence kind, omit a triggered loader/plugin/resource requirement, introduce an unknown requirement and make discovery incomplete; every case must prevent sparse execution even if the remaining predicates match. Start the standalone analyzer with only endpoints and schema selection, then demonstrate that a real matching G2 profile, inventory and baseline independently satisfy its descriptors and produce the two-target sparse plan; forged profile, inventory, receipt or predicate parameters must instead fall back. Verify evidence bound to another commit, profile or inventory is rejected. Test the ordinary target preflight, honest reporting of its observed target and stable-input assumption, independently of context validation; do not require proof of uninterrupted checkout identity or mid-run edit detection.

## Internal materialization and cache test seam

Keep non-public internal injection boundaries for Git object access, materialization, and cache read, refresh and atomic publication. Tests can supply deterministic failures and barriers while using the same production coordinator, without public flags or environment switches. Verify objects read are bound to the resolved immutable IDs even if symbolic refs or the live checkout change during analysis. Inject missing/corrupt objects, failed materialization or cache refresh/publication, and stale, wrong-policy, wrong-snapshot and incompatible-version cache entries; assert none becomes a current valid conservative result. Integrate real Git fixture tests through production wiring; do not use injected fakes as proof of actual Git behavior.

## Verification and risks

Construct small temporary Git repositories and assert exact report contents and fallback reasons. Cover diverged exact endpoint comparisons, missing endpoints, rejection of `worktree`, immutable object analysis despite live checkout edits or ref movement, missing objects and required submodules, materialization failures, absolute and parent-relative symlinks and chained escapes against external sentinels, loops and missing targets, safe contained links, path-component link escapes, and cleanup containment, deletion/rename, added overload or binding changing unchanged callers, both-revision provenance, unlimited dependency chains, ambiguous/unresolved calls, unsupported/dynamic behavior, parse and input failures, cross-project edges, resources, deterministic order and stale/incompatible cache isolation. Verify upstream base provenance and license. Compare repeated cold/warm outputs and exercise stale build failures. Tests must assert a fallback is required when coverage cannot be established, not merely that expected edges appear.

The largest risk is unsound exclusions from incomplete dependency models. Default conservatively to unbounded gaps until a construct and boundary are justified, even if sparse selection is initially rare. Parser and dependency loading, large snapshots and full resolution may be expensive; measure them but never truncate coverage for speed. The fork is public: avoid adding sensitive data and inspect upstream-bound changes before publishing.

## Out of scope and alternatives

Repository-specific discovery, ordinary test execution and practical target preflight, receipts and baseline compatibility, setup skill generation, and full integration acceptance live in subsequent goals. Worktree targets and their snapshot capture are deferred. Optional historical checkout execution is not required here. A fresh multilingual parser or graph service duplicates upstream work; using ordinary navigation `blast` output is unsafe because it drops information and truncates or groups for display. Treating same-name calls as complete coverage is insufficient for dynamic behaviors. A separate repository or subtree would conflict with the unified fork direction.
