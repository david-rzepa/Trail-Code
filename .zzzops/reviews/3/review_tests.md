# G3 expanded test review

Changes requested on one remaining part of finding 2. Findings 1, 3 and 4 have targeted tests that exercise their critical behaviors once setup is implemented: actual Go/Node test-body markers, Trail-code full fallback, missing discovery and mixed-language broadening, adapter failure/mismatch, and a malicious-content fixture that no longer terminates at the symlink check. The maintenance fixture exercises new projects, changed commands and user-owned edits. These new paths remain unmeasured because the setup implementation does not exist yet.

The fresh-package test only checks that a particular file exists in the tarball and returns success for `--help`. It never uses the packaged asset to set up a target repository or invokes its generated adapter. It would pass for a file whose help works but whose helper imports, assets, generation, or fresh-install wiring are missing. The design explicitly requires a fresh distribution to invoke the setup and not depend on the development checkout. Run actual setup from a freshly unpacked/installed package on a controlled fixture outside the source checkout, then invoke the generated adapter (a plan or small full operation is adequate for package wiring); make its package dependency setup reproducible and ensure it cannot accidentally import project source. This also checks the supported installation mechanism, rather than claiming package viability from a help command.

The test fixes exact `src/test-impact/setup-cli.ts` and packaged `dist/test-impact/setup-cli.js` paths. A CLI is an acceptable implementation choice, but the approved design only requires an explicit invocable skill and compatible packaged assets; it does not itself require this exact path or a new public CLI. The implementer should assess whether this is an appropriate production interface, and the test contract should follow that interface rather than imply an owner-approved CLI name.

The measured 8.5-second red run includes a real build/pack but otherwise stops at the absent setup entry point; it is not evidence of generated execution or production cost. The Trail-code full suite integration test has material cost but directly verifies the approved original workflow; remeasure after implementation and avoid unnecessary duplicate full runs. Tests do not require mid-run checkout mutation proof.
