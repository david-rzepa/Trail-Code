# Deterministic committed-snapshot planning, execution and evidence

## Outcome and owner decisions

Build the shared deterministic helper and a real Trail-code adapter directly in the fork, supporting explicit committed comparison endpoints on ordinary Git repositories across supported platforms. Do not invoke a model in normal runs. The original full test command and required build/setup/gates remain independently callable.

The source specification applies as amended by the owner's later decisions:

- Receipt format, Dave, 2026-11-03: “Versioned JSON files (recommended)”.
- Initial endpoint scope: the owner accepts committing work before a run: “even if we require that work is committed”. Worktree targets are deferred.
- Execution guarantee, Q1 (`review_design:5:1`), Dave, 2026-11-04: “Are you trying to solve the problem of proving that a checkout didn't change still? No test runner every bothers to prove that...” The recorded decision is to use normal test-runner execution assuming relevant checkout inputs stay stable during a run; do not require proof, filesystem snapshots, mutation monitoring, edit-and-revert detection or an isolated checkout as a verification prerequisite. Keep explicit committed endpoints and execute the intended target using ordinary Git checks and user workflow. This supersedes earlier design requirements to prove immutability or continuously detect changes.

## Planning and analyzer contract

Require both `--from` and `--to` for all plan and run modes and reject literal `worktree` clearly without substituting another target. Resolve symbolic refs once to immutable commit/tree identities; retain original user arguments separately in reports. Do not silently choose HEAD, a merge base or a previous run. Invoke G1's `trail impact --from <resolved-A> --to <resolved-B> --schema-version 2 --json` using an argv array. Its `comparison.requested` must equal the actual pinned argv, while resolved commit/tree IDs must equal the helper's once-resolved identities. A moving branch cannot change the selected comparison. Reject failed invocations, unsupported schemas, malformed or contradictory results, incorrect endpoint identity, unknown analysis status or model. Zero analyzer exit only means a report was generated.

G1's v1 default remains conservative and must not be interpreted as v2. Accept v1 only under its own supported schema and fallback rules; unsupported or missing conditional evidence cannot make it less conservative. V2 adds conditional results, `supported_model` and mandatory `context_requirements`; `conditional` means the analyzer has not validated execution context or passing tests. An unbounded gap or incomplete analysis demands full-profile fallback; bounded gaps must map to all dependent test targets or broaden to full profile. A malformed or unknown report cannot justify exclusions.

For conditional v2, the helper maintains an independently trusted, versioned model registry keyed by the exact model ID/version. The registry defines the complete mandatory singleton requirements (`runtime`, `runner`, `inventory`, `resolver`, `inputs`, `environment`, `baseline`), allowed typed predicates and parameters, collectors, evidence bindings, and deterministic triggers for each discovered loader, hook, plugin, fixture, service, generated or external resource, dependency and relevant environment input. Discover and derive the required singleton and triggered set independently of the report, including evidence that each discoverable class has been fully examined. Compare exact unique IDs, kinds, predicate shapes, parameters, subjects and evidence bindings against that independently derived set. Report omission, duplicate, weaker collector, unknown addition, unrecognized predicate, altered parameter, or incomplete discovery as unusable for sparse execution. The analyzer only supplies predicates and commit-derived parameters; it cannot invent or attest actual runner, profile, inventory, runtime, environment or receipt values.

Collect actual process runtime/platform/architecture, runner and adapter/version, discovery policy and target inventory, compiler/transpiler and resolver/loader configuration, committed and declared generated/external inputs, relevant environment descriptors, and compatible prior receipt using registry-prescribed independent collectors. Validate predicates against the actual evidence, binding each collector/version and observed digest to target commit/tree, profile, inventory, model and execution configuration. Revalidate context where needed before execution and receipt creation; this validates the specified context, not proof that source files never changed during the run. Missing, unsupported, stale, incomplete, forged, inconsistent or unmet evidence prohibits sparse execution and selects the complete configured profile, or returns incomplete if no valid full workflow can be established. Registry/model semantic changes invalidate incompatible plans and receipts. Never rely on a user assertion or a matching analyzer-supplied string as independent evidence. Preserve calculated impact separately from final executed scope and explain each requirement and fallback.

Consume G1's multilingual conservative Trail-code graph and its versioned language/build adapters rather than imposing a Node/TypeScript-only repository whitelist. Each component model must have independently verified supported constructs, complete mandatory requirement IDs and observed execution bindings. For mixed-language or cross-build projects require all component model identities, context sets and cross-language/build/resource relationships; an unknown boundary or unmapped component forces full-profile fallback. A bounded gap may name a build target, package or other explicitly evidenced boundary: independently validate the model, boundary, provenance and dependent-target mapping, then select every affected dependent test, including tests outside that scope and dependencies from both revisions. A directory name alone never proves a boundary. Preserve bounded selectivity when completeness is established; unbounded or unvalidated scope requires full fallback. Irrelevant documentation or metadata follows explicit applicable classification rules rather than blanket invalidation or an assumed filename exclusion.

Discover actual runnable targets at B, map impacts and scope dependencies, independently include new and modified tests and exclude deleted ones. Apply declared fixture, resource, generated-input, hook, configuration and build invalidations; unknown mappings, discovery failures, unsupported selectors, dynamic registration or uncertain dependency boundaries broaden to supported whole targets or full profile. Preserve original preparation, ordering, dependent groups, resource constraints and global gates; do not reinterpret whole-suite coverage thresholds over a subset. A genuinely empty selection requires complete discovery, valid analysis and compatible evidence. Plans are deterministic, ordered with stable reasons and preserve original runner ordering; changes to context, inventory, configuration, policy or model invalidate reusable plans.

## Representative adapter and execution

Use this fork's real Node/TypeScript workflow as the initial integration. Its `npm test` calls `scripts/run-tests.mjs`, discovers sorted `test/*.test.ts` files, sets Git overrides and `GRAFT_NO_TRAIL_SWITCH`, creates and cleans a temporary directory, and executes Node/tsx. Preserve `npm test` as an independently callable full fallback and retain `npm run build` and other configured gates. Add a real conventional Go module adapter/fixture with package-level `go test` units, real discovery, module/build configuration and independently verified Go version, GOOS/GOARCH, build tags, package graph and external dependency context. Its full module test command stays independently callable. cgo, generated/embed resources, unresolved imports or build conditions not proven modeled trigger a justified dependent-scope fallback or full profile. This is a second supported slice, not a claim that all Go projects are modeled. A selective file adapter must prove that it preserves these semantics, prerequisites, resource ordering and platform behavior; otherwise execute the entire suite. Config and commands are explicit data and argv arrays or intentional existing scripts, never executable text extracted from the impact report.

At run start use ordinary Git checks and repository configuration to ensure that the intended committed target is the checkout being tested and to catch a known mismatch; report the requested and resolved B, the actual checkout identity observed at start, and relevant known mismatch or dirty-state results. Do not reset or alter the user's checkout silently. Execute the existing workflow against the intended target. Assume relevant inputs remain stable throughout execution in the same manner as an ordinary test runner; no snapshots, watchers, special mounts, exhaustive before/after hashing, same-user edit-and-revert detection, or isolated checkout are required. Optional isolation may be added later but is not a condition of success. Do not claim that uninterrupted identity or absence of mid-run edits was proven. A known preflight target mismatch cannot validate B, and the report and receipt must describe the stable-input assumption rather than assert verified immutability.

Materialization used by analysis remains subject to G1's safe containment and symlink rules. G2 must not introduce path-traversal or unsafe cleanup, treat graph output as executable text, or silently read external files as if they were committed snapshot data. Follow ordinary runner semantics for execution; if a known unsupported or untrusted input means the declared profile cannot be validated, broaden or fail rather than silently omit it. Missing required submodules, unrepresented generated inputs or unavailable required external dependencies are configuration/verification gaps, not unchanged inputs.

## Evidence and receipts

Receipt reuse is opt-in through verified evidence, not an implicit baseline guess. After resolving A, load only successful local receipts matching A's complete source identity, requested profile and coverage, target inventory, runner/dependency configuration, relevant non-secret environment identity and analyzer/helper policy. Missing, malformed, unsupported, incomplete, cancelled, failed or incompatible evidence causes full-profile execution at B. Successful full verification creates B's receipt; a selective run creates B's receipt only if the A receipt is compatible and every required target and gate completed, recording the prior receipt dependency. Missing or corrupt chained records, arbitrary subsets, known invalidations and partial success never establish full evidence. Do not store sensitive values; fingerprint declared values using a policy appropriate for secrets, or use stable non-secret descriptors. Use versioned JSON files in a local repository-scoped store outside the checkout and its Git-controlled or potentially untrusted paths, under a user-owned private state root. Namespace it by stable repository identity; never read, import or migrate receipts from the checkout, Git contents, environment-specified arbitrary paths, or an untrusted shared cache. Before each read or write, verify the state root, namespace, path components, receipt file ownership and private permissions; reject symlinks, non-regular files and unsafe parents, and use directory-relative no-follow operations or a platform equivalent that prevents replacement between validation and use. Do not create a trusted store through a preexisting untrusted path. Fail closed to a full profile if receipt provenance cannot be established; fail verification entirely if even a safe full run or safe receipt publication cannot be established. Publish only after successful completion using exclusive creation and an atomic rename or equivalent, with collision/race handling and no partial or overwritten evidence. Bind each receipt and its entire predecessor chain to the trusted store and validate every link; content hashes alone do not authenticate untrusted receipts. A schema-valid tracked or copied-in JSON file is not evidence. The trust boundary protects against untrusted checkout content and other local users under filesystem access controls; it does not protect against a malicious process running as the same local user or against executing malicious tests with that user's privileges. Where that trust assumption does not hold, do not reuse local evidence. Treat no trustworthy record as missing. Receipt retention/garbage collection and importing CI receipts are future work. The exact on-disk schema and executable/config field spellings remain proposed interface details to be validated in implementation and review rather than silent assumptions.

Receipt identity includes target commit/tree, profile and target coverage, actual inventory, runner/dependency and environment configuration, analyzer/helper policy, supported model and validated requirement-set identity. For a conditional selective run, reuse a compatible A receipt only after validating the independently collected context, execute all required targets/gates, and record the prior receipt dependency. Receipts explicitly record that execution uses the normal stable-input assumption; they do not claim to prove no concurrent edits occurred. A full run can create B evidence without a compatible A receipt after the complete requested profile succeeds; a selective run cannot. Failures, cancellations, arbitrary subsets and known invalid preflight state never create full-profile passing evidence.

## Result and validation

Emit a versioned execution report distinct from the analyzer report: original and resolved endpoints, initial checkout observation, profile, inventory, model/version, each requirement and its independently observed status, baseline evidence, calculated impact, final units and fallback reasons, execution status, verification status, stable-input assumption and receipt ID only when a receipt was created. Avoid raw sensitive environment values. In JSON mode reserve stdout for one object and send child logs/diagnostics elsewhere. `--plan` writes no receipt and explicitly reports not run/not verified. Preserve underlying exit and signal diagnostics; use the spec's exit codes.

Use real temporary Git histories plus subprocess tests for exact endpoints, symbolic ref movement, omitted endpoints, worktree rejection, target mismatch, stale/malformed/unknown v1/v2 reports and status/fallback contradictions. Independently remove each required singleton, omit triggered requirements, substitute a weaker collector or evidence from another commit/profile/inventory, change model identity and make discovery incomplete: none may cause sparse execution. Demonstrate actual sparse execution, not merely a plan or full fallback, for both supported slices: a real Node/TypeScript fixture and a conventional Go module each have two independent test targets, a compatible baseline and independently satisfied requirements. In the Go fixture use separate packages A and B with tracked static imports; change A and assert `go test` runs A plus every dependent test package while excluding unrelated B, then compare against the full module run. Include inverse changes, deletion and import rebinding; verify build tags, platform and external dependency identities. Exercise Python and other representative project fixtures only for declared supported constructs and safe fallback, without implying complete language support. Test bounded uncertainties whose dependent tests cross the boundary, unbounded gaps, mixed-language/build dependencies and non-code classifications. Run analyzer on committed A and B without checking out either, including with an unrelated dirty checkout; this is separate from execution's ordinary target preflight. Dynamic loaders, runtime registration, generated or external resources, setup files and cross-test dependencies must broaden or include dependent targets. Verify unchanged full-command behavior, args, logs, global gates and no recursive fallback, plus JSON output isolation and cancellation/failure behavior.

Exercise full-baseline and selective-chain receipts, profile/context/inventory mismatch, untrusted or forged tracked receipts, unsafe symlinked/replaced receipt-store paths, incomplete writes and concurrent publication. Test normal checkout preflight and honest stable-input reporting; do not require detection of mid-run edit-and-revert. Verify analyzer materialization path containment and symlink behavior through G1's actual supported interface, while treating its internal injection seam as test-only. Real Git and runner tests are required alongside doubles. Snapshot-backed isolation, persistent coverage histories and imported CI evidence remain future work. Measure total discovery, analysis, preparation and test time in the end-to-end acceptance goal.
