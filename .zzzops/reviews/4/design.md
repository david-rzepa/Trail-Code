# End-to-end validation of sparse test execution

## Outcome and scope

Build reproducible release-gate evidence for the integrated analyzer, deterministic helper, generated adapter and setup skill in this Trail-code fork. Exercise the actual production interfaces and packaged setup, including Trail-code's own Node/tsx runner as G2 and G3 specify; do not introduce another selection implementation. Initial endpoints are explicitly committed Git revisions only. Reject literal `worktree` clearly without substitution. The owner’s later ordinary test-runner decision supersedes the original worktree capture and mutation-proof requirements: at run start perform ordinary Git preflight, reject known target mismatch or disallowed dirty state, and report the observed identity and assumption that inputs remain stable during the run. Do not require snapshots, watchers, special mounts, privileged operations, filesystem-specific features, continuous identity proof, edit-and-revert detection, or an isolated checkout to use or validate the product.

Exercise all applicable cases from `docs/test-impact/design.md` §13 with the owner-directed committed-endpoint and stable-input amendments; document the worktree-specific portions of cases 1, 4 and 5 as deferred rather than claiming they pass. Evidence identifies each case, outcome, supported platform and ecosystem, plus blocked or failed cases. Do not release a passing gate for unexercised applicable supported behavior. The v2 conditional sparse path is an explicit release requirement; a system that always falls back to full is not sufficient.

## Reproducible histories and execution

Use project-native Node testing and controlled temporary Git repositories with committed A/B trees, runnable targets, independently discovered inventories and explicit expected outcomes. Temporary test repositories are a harness isolation convenience, not a product runtime prerequisite. Generate a real adapter through G3 and use G1/G2 production interfaces; fake runners are suitable for controlled fault injection and assertion of planning semantics but must be complemented by a real Trail-code `npm test` integration, its preparation, and independent original full fallback. Reuse G1–G3 tests only when they actually demonstrate the integrated requirement, and add missing cross-component coverage rather than restating their unit assertions. Avoid live third-party systems: pin, fingerprint or explicitly cover all declared environment, external service and generated inputs under always-run or fallback rules.

Construct histories for no change, production/test modifications, new/deleted tests, deletions and uncertain renames, diverged histories, caller rebinding, cross-project dependencies, fixtures, hooks, resources, generated code, callbacks, reflection and dynamic registration. For every supported ecosystem/runner combination, test applicable patterns; unsupported features must cause a recorded sound fallback. Assert actual surviving affected units or a justified broader target, and full profile for unbounded uncertainty. Simulate parse/index failures and unreliable selectors. Repeat plans with identical identities, inventory, evidence and context to verify stable ordering and reasons. Test compatible platform behavior on ordinary Git repositories, including environments without Btrfs, mounts, elevated permissions or subvolume operations; record untested supported platforms as gaps rather than pass claims.

Introduce deterministic failures in disposable B histories. Establish compatible passing A evidence, then compare the selective plan and execution to the original full command at the same committed B, profile, runner context, preparation and gates. Assert affected failing tests detected by full execution are in the selective execution and cause failure; if safety requires full fallback, prove it. Include deletion, modified/new test and shared-fixture mutants, not merely a passing full run. Selective comparisons require the independently established compatible context and baseline, while missing/incompatible baseline must expand to full B. Count expected broad selection as valid rather than rewarding unsafe exclusions.

## Release matrix and conditional sparse selection

Assert observable report statuses, reasons, runner units, underlying process results and receipts for all applicable matrix cases: (1–3) missing endpoint errors, literal worktree rejection, exact diverged endpoint trees and deterministic plans; (4–5) requested/resolved B, actual checkout identity observed at start and clear rejection of known mismatch or disallowed dirty state; (6–9) changed/deleted tests, removed or renamed entities, changed bindings, unknown constructs and parse/index errors with sound scope; (10–13) unreliable runner mapping, missing/incompatible/corrupt or untrusted evidence, failed/interrupted/partial runs and empty inventory versus failed discovery; (14–17) original full command and all setup/gates without recursive wrapper, generated adapter without model/skill at runtime, version/snapshot/mode cache isolation and failed refresh, and prerequisite group, order and resource constraints. A `--plan` report cannot establish passing verification. Do not claim detection of concurrent edits, edit-and-revert, uninterrupted identity, or mutation protection; report the normal stable-input assumption in results and receipts. Verify analysis materialization containment and symlink safety according to G1 while allowing safe temporary test fixtures.

Exercise G1 v1 and v2 as distinct versioned contracts. V1 retains its conservative fallback rules; do not reinterpret a v1 result as v2. For v2, demonstrate a real two-target Node/TypeScript fixture with a compatible A receipt and independently collected, satisfied G2 model-registry requirements, where only the affected target runs and the full comparison confirms the result. Bind evidence to the relevant target commit/tree, runtime, runner, profile, inventory, resolver, inputs, environment, model/version and baseline. Independently remove every mandatory singleton and triggered requirement; introduce missing discovery, duplicates, unknown or weaker predicates, changed parameters, forged analyzer assertions, wrong model, stale collectors, and evidence from a different commit/profile/inventory. Every such case prohibits sparse execution and broadens to the full configured profile or reports incomplete when a valid full workflow is unavailable. Verify dynamic loaders, generated resources, services and cross-project dependencies add their required triggered conditions or conservative fallback. The report must distinguish calculated impact from actual execution and explain unmet requirements and fallback.

Verify receipt trust and chain validation including unsafe/symlinked paths, untrusted checkout-provided files, malformed/incomplete/corrupt data and concurrent publication. Successful full runs can establish a B receipt; selective receipts require compatible A evidence and all required targets and gates. Failures, cancellation, plans, arbitrary subsets, known preflight mismatches and missing context required to validate a full run or its receipt identity must not create full-profile passing receipts. Distinguish those failures from missing sparse-only conditional context: if a collector is needed solely to establish sparse eligibility, its absence forbids sparse execution but a successfully completed full profile may create a full-profile receipt when the independent full-run and receipt-identity requirements are satisfied. Add separate tests proving both outcomes; if the full workflow or identity is incomplete, report incomplete and issue no passing receipt. Preserve original symbolic user refs separately from once-resolved immutable analyzer argv and commit/tree identities; simulate moving refs to verify the comparison does not move. Test fresh packaged installation and generated adapter operation without model invocation, honoring G3's authority boundaries. Worktree targets and snapshot-backed isolation remain deferred.

## Measurement and evidence

Provide a reproducible benchmark procedure over named small and larger committed histories. Include both no-baseline full fallback and an independently validated v2 sparse case with compatible passing baseline. Record exact A/B commit/tree IDs, starting checkout identity, stable-input assumption, profile, inventory and unit counts, analyzer/helper/model/runner versions, platform, non-secret environment identity, receipt/cache state, command, exit/outcome, selection strategy and reasons. Measure total wall time and, where actually observable, analysis materialization, graph, discovery/mapping, build/setup and execution. If separate phase timing is unavailable, label it unavailable with its reason instead of inferring it or changing execution semantics. Compare against the separately callable original full command at B with equivalent context and preparation. Record cold/warm cache conditions, repeat count, ordering and summary, and fallback frequency over the explicitly identified corpus; record invalid, failed and unavailable observations rather than silently dropping them. Keep secrets, receipts and caches out of committed benchmark artifacts.

Document the per-case matrix, exact commands and outcomes, supported boundaries and measured end-to-end comparison alongside the harness. No arbitrary speedup threshold is imposed; selecting fewer targets is not itself evidence of a speedup. Experiments detect defects rather than proving all language or dependency behavior. A passing baseline must come from a successful compatible run; a plan alone cannot provide one.

## Risks, alternatives and validation

Require the harness to catch deliberately suppressed failing tests, forged baseline evidence, and unsound dropped v2 requirements. Isolate injected failures and clean temporary fixtures without resetting a user's checkout. Treat known defects as explicit release blockers until fixed or tracked with a non-passing gate, never silent exclusions. Changes in a supported model, ecosystem or contract trigger rerunning applicable gates. Validate focused cases first, then run the repository's canonical build and complete verification on the integrated implementation, recording exact platform and limits.

Reject test-count-only or exit-only comparisons because they can hide omitted failures or lost gates, timing only test processes because setup/indexing may dominate, and fake-runner-only evidence because it does not prove the real runner integration. Tests operate under the same stable-input assumption as the ordinary test runner; earlier source-design language requiring proof of mutation protection and worktree snapshot acceptance is superseded. No package publishing, deployment, imported CI evidence or unsupported runtime instrumentation is part of this goal; any optional CI integration remains subject to separate authorization.
