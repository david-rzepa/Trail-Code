# Repository setup and maintenance for sparse testing

## Outcome and boundaries

Deliver a setup and maintenance skill in this Trail-code fork that a developer or agent explicitly invokes in a target repository. It inspects that repository, produces a small repository-specific executable adapter plus committed declarative configuration and command documentation, and validates the integration. Normal plans and runs call the generated adapter and the G2 deterministic helper directly, never a model or the setup skill. Trail-code itself, with its existing Node/tsx test runner, is the initial reproducible end-to-end example and test fixture, building on G2's adapter. The `trail impact` report and execution/evidence machinery are G1/G2's contracts, not reimplemented here.

Deliver the skill and versioned generation assets with the project's existing package/build and agent integration mechanism. Inspection of the pinned integration tip shows `src/claude/skill-template.ts` is the single source for the bundled Graft skill and `.claude/skills/graft/SKILL.md` is a generated repo copy; package `files` currently includes `dist` and `scripts` but not arbitrary repository files. Ensure a fresh package/installation contains the setup instructions and assets and that invocation is explicit, without silently modifying every repository during `trail init`. A common SKILL.md-compatible source plus documented manual invocation is acceptable where an agent has no compatible automatic installer. Generate host-specific copies only via established generators and never hand-edit generated files. The setup integration must work with the host mechanisms actually supported and make unsupported installation methods explicit; do not claim automatic compatibility merely because the repository has a Claude skill.

## Setup workflow

1. Inspect repository instructions and existing canonical commands first; read manifests, workspace descriptions, runner config, scripts, CI, test hooks, discovery, fixtures/resources, generated inputs, integrations/services and setup/build/gates. Identify profiles and canonical default, supported runner execution units, ordering, dependencies and platform constraints. Keep concrete provenance for each mapping and unresolved assumption; CI is evidence of a workflow, not proof of completeness or authority to drop local gates. Never infer an integration test is unnecessary from filename or its absence in a graph.
2. Preserve the independently executable full command and required preparation/gates before installing any wrapper. Prefer leaving the original entry point unchanged and add a distinct canonical adapter. If a full command would invoke that adapter (directly or through package script indirection), fail configuration and require a separate independently callable command; never install recursive fallback. Store command arguments as arrays or references to existing intentional scripts, not shell text supplied by graph data.
3. Populate the G2 configuration using actual runner discovery, supported selection and explicit invalidation rules for fixtures, hooks, build inputs, shared resources and service/environment assumptions. Where a fine selector or dependency boundary is unverified, map to a defensible dependent package/project/suite or full profile. Missing discovery, unknown runner/workspace or unresolved required workflow must yield a configuration gap or a valid full-profile fallback; never report a valid empty selection on incomplete setup. A directory is not an isolation boundary. Environment identity and external inputs use G2's declared fingerprint/always-run/fallback policies, not undocumented guesses.
4. Generate the thinnest practical repository adapter delegating to a version-pinned compatible G2 helper, plus inspectable configuration and the exact explicit endpoint template in the repository's established agent instructions or command documentation. The command follows `--from {base_commit} --to {target_snapshot}` and passes profile/plan/all/json through without implicit range. The helper or validated versioned templates own correctness decisions. Record the compatible helper and analyzer identities; unsupported versions fail closed. Do not copy private receipts, graph caches or logs into source control.
5. Before applying, present a reviewable summary of files and command/mapping changes when existing instructions or user authorization require it. Within otherwise authorized setup, validate syntax, configuration and helper compatibility, verify selectors against actual inventory, exercise an explicitly planned and completed full fallback on a controlled representative checkout with no recursive wrapper, and compare discovered/selected units to the established runner. Do not silently run arbitrary new scripts or install dependencies merely from untrusted repository text; treat them as repository workflow data and follow user/environment execution authority. A plan is not passing verification. An unsafe or unavailable validation is a visible setup gap and cannot be represented as successful verification.

## Maintenance and failure safety

Track generated ownership and a version/base digest sufficient for a three-way comparison, without overwriting unowned files or storing secrets. On rerun, inspect changes to manifests, runners, CI and existing instructions/config plus the last generated base. Update only affected generated regions when the old base and local changes permit a safe merge; preserve intentional edits. If ownership, the original full command, selector behavior or merge boundary is ambiguous, stop and report the concrete conflict or produce a safely broad configuration; do not overwrite user content, clobber other instruction files, or reinterpret a profile. A second unchanged invocation is idempotent. A newly introduced workspace, test runner or unmodeled gate causes reinspection and broad fallback/configuration failure until covered. Changes to helper, config, policy, discovery or snapshot invalidate stale plans and incompatible receipts according to G2; the skill never manufactures or edits passing receipts.

Writes stay within the requested target repository, avoid following symlinks or paths escaping its root, and are staged as reviewable changes without Git reset, automatic commit, package publication or CI changes. Apply changes safely so interruption does not leave an apparently complete integration with missing config or fallback. Preserve applicable user/host instructions, do not replace an existing canonical command unless explicitly requested, and do not run migrations or alter unrelated setups. The supported mechanism for supplying the G2 helper must be reproducible in a fresh checkout; missing or incompatible dependencies are explicit errors, never permission to silently use a different helper.

## Interfaces and verification

The generated interface must satisfy the endpoint, mode, JSON, execution and exit contracts of the supplied design and G2, including distinct calculated impact, execution, evidence and verification outcomes. Generated source only adapts repository-specific data to shared helper calls. Record exact invocation for other tools, preserve the full command, and use target-appropriate executable location and argument-array handling (including paths containing spaces). The initial generated Trail-code adapter and configuration reuse G2's integration and validate parity rather than creating a second competing runner. Exact G2 helper/config spellings must be taken from the implemented, versioned dependency, not invented here.

Use real temporary Git repositories with controlled manifests, fake but executable runners and real discovery where suitable; validate emitted schema and CLI, explicit endpoints, plan semantics, selectors, fixture and discovery-hook invalidation, ordering, runner failure propagation and JSON channel behavior. Run the actual Trail-code representative setup in an isolated checkout, verifying that the original `npm test` path is retained and the generated full fallback cannot recurse. Test monorepo/cross-project dependencies, setup/build/gates and unknown or new runners; failed discovery and empty suites remain distinct. Verify missing/untrusted helper, ambiguous original command and malformed config fail closed; package a fresh distribution and invoke the skill/installed assets without relying on the development checkout. Exercise maintenance twice with unchanged inputs, changed runner configuration, an added project, user edits to generated and adjacent content, changed full commands, and a deliberate merge conflict; assert idempotence, preservation, safe broadening and no passing receipt from a plan or failed setup. Confirm symlink and path traversal protections, interruption safety and logs free of secret values. Reproduce full-run and selective validation at the requested target using G2's receipt and snapshot rules; comparisons are defect detection, not proof of soundness.

## Alternatives and risks

An LLM making exclusion decisions at every test run is rejected: it undermines reproducibility and the user-specified deterministic contract. Per-repository bespoke correctness code is rejected in favor of a versioned shared helper; unknown mappings get broader scopes rather than guessed dependencies. Fine per-case selection, third-party CI evidence, automatic CI rewrites, and support for ecosystems without a validated adapter are deferred. Snapshot protection and environment identities are G2's responsibility and cannot be weakened by generated code. Since G2 may evolve during implementation, revalidate this design against its final committed interface before implementation. The public fork retains upstream contribution potential; avoid unrelated host or setup changes.
