# Conservative two-snapshot impact analysis

## Outcome and scope

Extend this public Trail-code fork directly with deterministic, conservative impact analysis, preparing the change for a future upstream pull request. The analysis supplies a versioned report describing affected code and unresolved coverage, not a test execution or passing result. The consumer must broaden or refuse verification when the report cannot safely support exclusion. The requirements and 17-case acceptance matrix in `docs/test-impact/design.md` remain authoritative; this design focuses on the analyzer foundation and does not duplicate the adapter or setup skill.

## Owner decisions

## Approach

Work directly in `https://github.com/david-rzepa/Trail-Code`, integrating on `test-impact` from upstream base `ca20a67764e99531a1cf272eea8354e2c16f71d9` (Trail-code 0.28.0, MIT). Preserve the separate Unity plugin branch and upstream attribution and license. Build changes as an upstreamable extension in this repository; no separate repository or Git subtree is involved. Use existing parser, per-file facts, resolution and graph traversal. The current `src/graph/resolve.ts` deliberately drops unresolved calls, `src/blast/diff.ts` implements navigation-oriented ranges, and `src/blast/blast.ts` uses presentation groups. Add a separately identified conservative path instead of changing their meaning or consuming their `testModules` as a test inventory.

Resolve both requested refs once to commit/tree identities using argument arrays. Compare those exact trees, not their merge base. Capture and analyze each snapshot independently; a `worktree` target includes staged, unstaged, relevant untracked files, deletions and meaningful metadata, including declared relevant ignored/generated inputs, subject to a complete enumeration policy. Source materialization must not silently modify the user's checkout. Capture itself must be coherent: either obtain a genuine point-in-time filesystem snapshot covering every relevant root, or establish reliable observation or serialization before enumeration and keep it in force across enumeration, reads and snapshot sealing. Observation must cover directories and inputs that can become relevant, so additions, removals, renames, metadata changes and edit-and-revert are detected; detect event overflow, watcher loss, unsupported filesystems and any loss of coverage. Invalidate the whole capture and retry or fail clearly on any relevant mutation or loss of observation; before-and-after hashes or best-effort watchers alone are insufficient. Do not fingerprint, analyze or claim a successful worktree snapshot if coherence cannot be established. A later full-suite fallback cannot validate an uncaptured or synthetic target. Preserve source identities and snapshot fingerprints; if a snapshot or required submodule is unavailable, emit an explicit incomplete outcome and no misleading result. The execution layer is responsible for proving it executes that target and for mutation protection; an analyzer fingerprint alone cannot prove that no edit-and-revert occurred during execution.

Build file facts per snapshot using existing extraction caches only when extraction contracts match. Extend extractor and resolver outputs to record evidence and limitations rather than dropping unresolved candidates, parse failures or unsupported relevant input. Retain every defensible candidate and full provenance; represent unresolved bounded scopes explicitly. Unknown or unbounded behavior, unknown scope boundaries, incomplete input enumeration and analysis failures produce an unbounded gap requiring full-profile fallback. A successful parser invocation or absence of an edge does not imply completeness. Treat reflection, dynamic dispatch, callbacks, registration, subprocesses and resources as potential gaps unless modeled or safely bounded; document language-specific supported constructs and demonstrate why a scope is safe before labeling it bounded. External/environment inputs remain execution-layer configuration and must not be inferred unchanged from Git.

Perform a whole-graph resolution per snapshot after reusing compatible raw facts. Compute reverse closure without hop or count caps on old and new graphs separately, retaining revision provenance and scope-level dependencies. Seed old and new entities for changed files; use old edges for deleted entities/files and new edges for additions and new bindings. A conservative file/scope seed can broaden beyond changed lines where symbol attribution is uncertain. Where rename identity is ambiguous, treat as delete plus add. Re-resolve unchanged callers after symbol table changes. Emit all affected files/entities plus justified scope fallback, not only nodes that resemble tests. Any cross-scope boundary not demonstrably complete widens to the whole profile.

Use a separate conservative cache namespace and atomic writes. Keys include snapshot identity, path and content/metadata as relevant, analyzer and grammar/extractor/resolver versions, configuration, and conservative policy/mode. Graph caches may only satisfy the exact identity and successful complete refresh; stale data, failed writes or unsupported cache versions never masquerade as current. Prefer rebuilding to unsafe cache reuse. Stable path ordering and reason ordering make identical inputs produce identical reports.

## Report contract

Implement and validate schema version 1 as described in `docs/test-impact/design.md` section 8. Include `schema_version`, `analysis_identity`, `comparison` (requested and resolved endpoints, tree/snapshot identities), `changes` (old/new paths and entities), `affected` (complete files/entities and revision/reason provenance), `analysis_gaps`, `required_fallback_scopes`, and `analysis_status`. Define enumerated gap/status variants and a schema/validator in the implementation; reject unsupported versions and missing mandatory identity or status. Stable, structured reasons must distinguish direct changes, graph dependencies and fallbacks. A bounded gap identifies both the scope and the rationale for its boundary; an unbounded gap demands full-profile fallback. Deterministic sorting and canonical identity calculation are part of the contract. No graph-derived text is executable shell input. The impact report is distinct from the downstream plan, runner inventory, execution result and receipts.

### Observable analyzer interface

`trail impact --from <commit> --to <commit|worktree> --json` requires both options exactly once; help/version are exempt. Commit values are resolved once with Git to immutable commits and trees. `worktree` is valid only as `--to` and its capture obeys the coherence rules above. An unknown ref, invalid or missing option, unavailable snapshot, or inability to establish coherent capture returns nonzero (2 for invalid input or incomplete invocation), does not emit an apparently valid report, and writes diagnostics to stderr. `--json` writes exactly one JSON object to stdout for a completed analysis, with diagnostics on stderr. Exit 0 means the report was produced, including when `analysis_status` requires fallback; it never means tests passed or verification succeeded. No model calls are made. Existing `trail blast` semantics stay unchanged.

The following minimum v1 shape makes acceptance tests and adapters observable; all arrays are present even when empty, and all paths are repository-relative POSIX strings. Object fields listed below are mandatory unless explicitly nullable. Unknown schema versions are rejected; the downstream validator must treat malformed or unknown status, missing required fields or a contradictory status/fallback as unusable and broaden or block. Additions that consumers do not understand never justify a narrower selection.

- `schema_version`: integer `1`.
- `analysis_identity`: object with nonempty strings `analyzer_version`, `grammar_identity`, `extractor_identity`, `resolver_identity`, and `policy_identity`, plus `mode` equal to `conservative`.
- `comparison`: object with `from` and `to`. Each has `requested` (the literal argument), `kind` (`commit` or `worktree`), and `fingerprint` (nonempty content identity); commit endpoints additionally have `commit` and `tree` (full Git object IDs). `from.kind` must be `commit`; `to.kind` is `worktree` only for the explicit worktree request. The worktree fingerprint represents the coherent captured content and metadata, not a claim about future execution.
- `changes`: array of objects with `kind` (`added`, `modified`, `removed`, `renamed`), `old_path` and `new_path` (strings or null). Added requires only new; removed requires only old; modified requires both equal paths; renamed requires both distinct paths. Include old and new entity references where available as `old_entities` and `new_entities`, arrays of identifiers. An uncertain rename is represented as removal and addition.
- `affected`: array of objects with `revision` (`from` or `to`), `path`, `entity` (string or null for file/scope impact), and nonempty `reasons` array. Each reason has `kind` (`changed`, `dependency`, or `fallback`) and `detail` (nonempty string); dependency reasons carry their supporting relationship/provenance. Output retains all relevant old and new impacts without result truncation; it does not filter by test filename.
- `analysis_gaps`: array of objects with `revision` (`from` or `to`), `path` (string or null for global gaps), `kind`, `detail`, and `scope` (null for unbounded, or a nonempty declared scope identifier). Reasons include parse/index failures, unresolved constructs, unsupported or unmodeled behavior, and missing required input.
- `required_fallback_scopes`: array of objects with `kind` (`scope` or `full_profile`), `scope` (nonempty identifier for `scope`, otherwise null), and `reason` (nonempty). Every unbounded gap requires `full_profile`; bounded gaps require an appropriate dependent scope or full profile. Scope identifiers are data, not shell fragments, and the adapter must be able to map them to dependent targets or fall back to the full profile.
- `analysis_status`: `complete` only when the supported model has no uncovered gaps, `bounded` when every gap is covered by explicit bounded fallback, and `incomplete` when any gap is unbounded. An incomplete report always has a `full_profile` fallback. A valid empty impact has an empty `affected` array and no gaps; it is distinct from a failed capture or incomplete report.

Order changes, affected entities, gaps, fallback scopes and reasons by stable documented keys; all identity and policy inputs are included in cache keys. Test the CLI as a subprocess against temporary repositories, validate every required field and type, and check that malformed/unsupported schema data cannot be used to justify exclusions. Include explicit error, incomplete-with-fallback and valid-empty examples. A worktree snapshot identity cannot substitute for execution-layer mutation protection.

## Internal capture and cache test seam

Keep a non-exported internal orchestration boundary (importable by repository tests, not a package export, environment variable, CLI flag or supported user interface). Inject a capture backend and cache store into the analyzer: production wiring selects the real backend/store; tests supply deterministic fakes or wrappers while exercising the same coordinator and validity decisions. The capture backend exposes acquisition, enumeration, reads, sealing and cleanup, and an explicit strategy/result identifying a coherent immutable snapshot or an observed live capture. For the latter, it exposes established observation coverage and mutation/loss signals across all relevant roots. The cache store exposes read, refresh and atomic publication results, including identity, failed refresh/write and stale or incompatible entries. Barriers at observation establishment, enumeration, individual reads and sealing permit deterministic file mutation and observer-event injection; tests release barriers rather than sleeping. Production behavior must not depend on test hooks.

Test a genuine point-in-time backend by changing the live tree after snapshot acquisition and proving that all captured files and inventory come from one immutable snapshot identity; concurrent live edits need not invalidate that snapshot. Test the observed-live backend by injecting changes, additions, renames, edit-and-revert, overflow and observation loss at the barriers: the coordinator must retry or return explicit unavailability, never issue a successful fingerprint for the invalid attempt. Test that a backend unable to establish complete coverage returns unavailable. Inject failed refresh/publication and stale, wrong-policy, wrong-snapshot and incompatible-version cache entries, and assert that none is returned as a current conservative result; any successful rebuild must have the correct identity. Include at least one integration test through real production wiring where the host supports a reliable capture backend and assert coherent success or explicit unavailability, not a manufactured guarantee from the fake. Fault seams supplement rather than replace real Git fixtures and subprocess contract tests.

## Verification and risks

Construct small temporary Git repositories and assert exact report contents and fallback reasons. Cover diverged exact endpoint comparisons, missing endpoints, staged/unstaged/untracked and declared ignored inputs, concurrent changes, additions, renames and edit-and-revert during enumeration and reads, watcher overflow or lost observation (each must retry or fail without a valid capture), deletion/rename, added overload or binding changing unchanged callers, both-revision provenance, unlimited dependency chains, ambiguous/unresolved calls, unsupported/dynamic behavior, parse and input failures, cross-project edges, resources, deterministic order and stale/incompatible cache isolation. Verify upstream base provenance and license. Compare repeated cold/warm outputs and exercise stale build failures. Tests must assert a fallback is required when coverage cannot be established, not merely that expected edges appear.

The largest risk is unsound exclusions from incomplete dependency models. Default conservatively to unbounded gaps until a construct and boundary are justified, even if sparse selection is initially rare. Parser and dependency loading, large snapshots and full resolution may be expensive; measure them but never truncate coverage for speed. The fork is public: avoid adding sensitive data and inspect upstream-bound changes before publishing.

## Out of scope and alternatives

Repository-specific discovery, test execution, receipts and baseline compatibility, mutation observation during execution, setup skill generation, and full integration acceptance live in subsequent goals. Optional historical checkout execution is not required here. A fresh multilingual parser or graph service duplicates upstream work; using ordinary navigation `blast` output is unsafe because it drops information and truncates or groups for display. Treating same-name calls as complete coverage is insufficient for dynamic behaviors. A separate repository or subtree would conflict with the unified fork direction.
