# End-to-end validation of sparse test execution

## Outcome and scope

Establish an executable, repeatable release-gate suite and recorded performance evidence for the integrated analyzer, helper, generated adapter and setup skill. Exercise the actual production interfaces and packaged setup, including Trail-code's own Node/tsx runner as G2 and G3 specify; do not introduce a second selection implementation. The project runs directly in the public Trail-code fork. This goal follows their final integrated implementations and revalidates its harness against the delivered contracts rather than inventing CLI or configuration fields.

All 17 acceptance cases in `docs/test-impact/design.md` §13 are mandatory release gates, not merely an illustrative matrix. Results must identify each case, evidence, supported platform/ecosystem, and any blocked or failing case. Unsupported ecosystems and assumptions are listed explicitly, and no passing release result is produced for an unexercised supported case. The goal tests product behavior and its supported dependency model, but full-suite comparison is defect detection, not a proof of soundness.

## Reproducible harness and fixture histories

Use project-native Node test infrastructure and isolated, deterministic temporary Git repositories with committed A/B trees, explicit runner units, recorded discovery and expected behavior. Include a real generated adapter via G3, not a test-only reimplementation. Use fake runners only for controlled fault injection and assertion of planning/execution semantics; additionally exercise Trail-code's actual `npm test` preparation, runner integration and full fallback in an isolated checkout. Existing G1–G3 tests may serve a matrix case only where the full integrated path is exercised; retain their fast unit tests and add missing end-to-end coverage instead of duplicating identical assertions. All test inputs, including external services or environment, are pinned, fingerprinted, or explicitly always-run/fallback; do not rely on live third-party systems.

Create representative histories covering no change, production and test modification, added/deleted tests, deletions, uncertain renames, diverged histories, caller rebinding, deep/cross-project dependencies, shared fixtures, discovery hooks, resources, generated code, callbacks, reflection and dynamic registration. For every ecosystem/runner adapter the integrated product claims to support, exercise these applicable patterns or explicitly demonstrate that an unsupported pattern yields a sound documented fallback. Assert specific surviving impacted units or broader justified scope; where unbounded require full profile. Inject parse/index failures and unreliable selectors. Filesystem races use controlled synchronization or G1's non-public injection seam; also test actual production wiring as specified by dependencies. For a platform without reliable snapshot protection, assert explicit failure or valid fallback; never claim validation after observation loss.

Use test failures introduced into disposable histories: establish a successful compatible A baseline and assert that affected failing tests in B are executed and make the result fail even where graph uncertainty forces full fallback. Compare full and selective results at the same protected B with equivalent setup, inventory, context and declared gates. Verify every actually failing unit detected by the full run is included/executed in the selective run, and that a selectively successful receipt is issued only after compatible reused evidence plus successful required targets. Selection may be broader than necessary; a no-baseline case must run full. Include deletion, modified/new test and shared-fixture mutants so a coincidental full pass is not the sole evidence. Exact suite semantics matter: comparison must honor configured profile, preparation, ordering and gates, not substitute a filtered command for the original full workflow.

## Release matrix and negative paths

For every named case, assert observable report statuses, reasons, runner units and process results, not just output formatting. At minimum cover: (1–3) missing endpoint rejection, exact diverged trees and ordered repeatability for identical inputs; (4–5) requested versus executed snapshot identity, staged/unstaged/untracked/deleted/metadata inputs, coherent capture and edit-and-revert or observation loss; (6–9) changed tests, deleted/renamed entities, changed bindings, unknown or unmodeled constructs and parse/index errors with conservative scope; (10–13) unreliable runner mapping, absent/incompatible/corrupt/untrusted baseline evidence, failure/interruption/partial runs and empty inventory versus discovery failure; (14–17) original full command and all setup/gates without recursion, standalone generated adapter without model/skill at runtime, mode/version/snapshot cache isolation and failed refresh, plus prerequisite group, order and resource constraints. Preserve child errors, distinguish plans from verification and enforce no receipt on invalid, incomplete or interrupted runs.

Exercise G2 receipt trust and chain validation, symlink/unsafe paths and policy/schema incompatibility, including successful full and selective receipt chains and refusal of repository-provided forged evidence. Test worktree mutation through the capture and execution lifetime using deterministic barriers; ensure the asserted outcome matches the actual supported protection mode (a genuinely immutable captured snapshot remains valid while edits to the original occur, whereas an observed-live target must invalidate on relevant edits or observation loss). For committed historical B, prove execution is of B or an explicit target-mismatch result; never count full fallback at another checkout as validation. A fresh package/install and controlled generated repository must run using the distributed helper without invoking a model, while respecting G3's inspection and command-authority boundaries.

## Measurement and evidence

Add a reproducible benchmark procedure using representative small and larger histories, including a no-compatible-baseline full fallback and at least one compatible-baseline selective case. Capture exact immutable A/B and target fingerprints, profile, inventory count, analyzer/helper/runner versions, platform and non-secret environment identity, receipt and cache state, command, outcome, selection strategy/reasons, fallback occurrence and selected/total units. Record wall-clock snapshot preparation, graph work, discovery, mapping, build/setup, execution and end-to-end elapsed time; where existing production instrumentation cannot separate a phase, mark it unavailable with reason rather than infer or change semantics for measurement. Run comparable selective and independent original full commands at B with equivalent preparation/context; label cold and warm cache conditions and use repeated measurements with a stated count, ordering and summary. Report fallback frequency over the actual explicitly identified corpus, not an extrapolated population. Keep logs and artifacts free of credentials and private input content; do not commit generated receipts or caches.

Make the evidence readable and reproducible in repository documentation alongside the harness, with per-case status and a concise comparison of end-to-end cost, selection count and fallback frequency. Performance claims require recorded actual observations, and selecting fewer units alone is not proof of speedup. No arbitrary speedup threshold is introduced; an expensive or uncertain analysis may properly select the full suite. Record failed, invalidated and unavailable observations rather than dropping them. A verified full run at B supplies the necessary compatible baseline only when all receipt rules are satisfied; plans and failed runs never do.

## Failure handling, alternatives and verification

Each fixture should fail if an impact is omitted, a fallback weakens the required profile, stale evidence is reused, execution does not match target, or a receipt is created improperly. Injected failures must be isolated and removed through temporary worktrees without resetting the user's checkout. Known defects found while exercising the matrix are fixed within scope if practical; otherwise make them explicit actionable blockers rather than mark the release gate passed. Changes to supported ecosystems or interfaces invalidate the applicable coverage and require rerunning the matrix.

Reject comparing only test counts, successful exits, or graph snapshots: these can mask missed failures and setup/gate omissions. Reject timing only test processes, because snapshot, indexing and setup may erase any savings. Reject relying solely on artificial runners, because they cannot prove the real integration; reject running only the full existing suite, because it does not exercise conservative selection or fallback.

Validate the harness itself with known-good and deliberately bad fixtures, including a suppressed affected failure and invalidated receipt, so the gate detects an unsound selector. Run the focused matrix first, then the repository's canonical build and full verification appropriate to the integrated implementation. Report exact commands and results, including platforms and unsupported cases. CI wiring is only added if authorized separately and does not replace these release checks. This goal does not publish packages, deploy services, add external CI receipt imports, or implement unsupported runtime instrumentation.
